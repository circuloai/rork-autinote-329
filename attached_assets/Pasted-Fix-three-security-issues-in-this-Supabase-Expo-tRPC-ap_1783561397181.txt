Fix three security issues in this Supabase/Expo/tRPC app (AutiNote). Work through them in order.

## 1. (Critical, do this first) Password reset code has no rate limiting — brute-forceable account takeover

Files: expo/backend/trpc/routes/auth/forgot-password/route.ts, expo/MIGRATION_PASSWORD_RESET.sql

The reset code is 4 digits (10,000 possibilities) valid for 10 minutes, and nothing limits how many times `verifyCode` or `resetPassword` can be called. An attacker who knows a victim's email can brute-force the code with a script and take over the account.

Add both:
a) Database-level attempt tracking on `password_reset_codes`: add columns `attempt_count INTEGER DEFAULT 0` and `locked_until TIMESTAMPTZ`. In `check_reset_code` and `verify_reset_code_and_update_password`, increment attempt_count on every failed check for that email's active code row, and once attempt_count reaches 5, set locked_until = NOW() + INTERVAL '15 minutes' and reject all checks (even correct ones) until that time passes, returning a generic "too many attempts, try again later" message. Reset attempt_count to 0 whenever a new code is generated via create_password_reset_code.
b) Per-email cooldown on `create_password_reset_code` itself: reject (or just silently no-op with the same generic success message) if a non-expired code was already issued for that email in the last 60 seconds, so requestCode can't be used to flood-generate codes either.

Write this as a new file MIGRATION_RATE_LIMIT_RESET_CODES.sql (idempotent, safe to re-run, following the style of the existing MIGRATION_*.sql files — DROP/CREATE FUNCTION, REVOKE/GRANT to service_role only). Update route.ts only if the RPC response shape changes (e.g. a "locked" flag) so the UI can show a clear message.

## 2. Consolidate the shared_access RLS migrations so the privilege-escalation fix can't regress

Files: expo/DATABASE_SCHEMA.md, expo/MIGRATION_THERAPIST_INVITES.sql, expo/MIGRATION_FIX_RLS_AUTH_USERS.sql, expo/MIGRATION_FIX_ACCESS_CONTROLS.sql

DATABASE_SCHEMA.md and two of the migration files still define a "shared_access_therapist_update" / "Therapists can update their invitations" policy with a USING clause but no WITH CHECK, which lets a therapist overwrite any column on their own shared_access row (can_export, can_add_notes, can_view_profile, readonly_mode) instead of just accepting/declining. MIGRATION_FIX_ACCESS_CONTROLS.sql correctly drops this policy, but only if it's run last, by hand, after the others — there's no versioning to guarantee that.

Do this:
a) Update DATABASE_SCHEMA.md so the canonical schema it documents matches the final, fixed state (i.e. it should NOT include the open "Therapists can update their invitations" policy at all — invite acceptance only via accept_therapist_invites()/accept_invite_by_token()).
b) Add a numbered ordering to the migration files (e.g. rename or add a MIGRATIONS_ORDER.md / header comments stating "Run after: X, Run before: Y") so a fresh deploy can't apply them out of order.
c) Add a verification query or a small script (scripts/verify-shared-access-policies.sql or similar) that checks no UPDATE policy on shared_access lacks a WITH CHECK clause, so this can be re-checked after any future migration.

## 3. Default therapist invite grants full permissions immediately

File: expo/app/settings/invite-therapist.tsx

New invites are created with can_view_logs, can_view_progress, can_view_profile, can_add_notes, can_add_sessions, can_comment, can_export all set to true and readonly_mode false — full access before the caregiver has reviewed anything. Change the defaults in the `accessData` object to a more conservative starting set (can_view_logs: true, can_view_progress: true, can_view_profile: true, everything else — can_add_notes, can_add_sessions, can_comment, can_export — false, readonly_mode: true), and update the "Default Permissions" info card copy in the same file to accurately describe the new defaults. Keep the ability for the caregiver to upgrade permissions afterward (existing settings screens) unchanged.
